# End-to-end test

The suite runs only against a kind cluster whose kubeconfig is named on the command line, in `E2E_KUBECONFIG`, and refuses any other: [`guard.go`](guard.go) wants a single context whose name starts with `kind-capl-e2e` and whose server is a loopback address, as kind writes it, so it never reaches a cluster through the current kube context or one that only carries the name.
The prefix is not Lodia's `lodia-e2e`: this guard refuses Lodia's own e2e cluster, `kind-lodia-e2e-local`, in which the suite would upgrade Lodia, and Lodia's guard refuses this one.
It also refuses to start while a `HELM_KUBE*` variable is set, since helm [lays them over](https://github.com/helm/helm/blob/v4.3.1/pkg/cli/environment.go#L97-L130) `--kubeconfig`.

`make e2e` creates the kind cluster `capl-e2e`, runs the suite and deletes the cluster.
`E2E_CLUSTER` changes the name.
`make e2e` refuses, before it creates anything, a name that does not start with `capl-e2e`, that has a character outside `a-z`, `0-9` and `-`, that ends in `-w` or that is longer than 30 characters.
The prefix is the one the guard wants, and a name ending in `-w` is refused because a run named `x` removes the containers labelled `x-w`, which are also the nodes of a kind cluster named `x-w`.
The Cluster is named `<E2E_CLUSTER>-w`: CAPD [labels](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/infrastructure/docker/internal/docker/util.go#L31) its containers with the Cluster's name in kind's own [label](https://github.com/kubernetes-sigs/kind/blob/v0.33.0/pkg/cluster/internal/providers/docker/constants.go#L21) for the nodes of a cluster, so that name must not be the kind cluster's, and Lodia [requires](https://github.com/lodia-io/lodia/blob/57375832e7fe8b3a06374613797eb4c544fe7612/api/v1alpha1/controlplane_types.go#L17) the name of the `ControlPlane`, the Cluster's, to be a DNS-1035 label of at most 32 characters.
The cluster has one node of kind's default image, with the Docker socket that CAPD needs and the admission plugin `OwnerReferencesPermissionEnforcement`, which [refuses](https://github.com/kubernetes/kubernetes/blob/v1.37.0/plugin/pkg/admission/gc/gc_admission.go#L149) an owner reference with `blockOwnerDeletion` to an object whose finalizers the writer cannot set.
After it creates the cluster and again at the end, `make e2e` removes the containers labelled for the Cluster, with their volumes; on a Linux host, delete the cluster of a killed run first: `go tool kind delete cluster --name capl-e2e --kubeconfig work/e2e/capl-e2e/kubeconfig`.

The suite needs Docker and helm on the `PATH`, and runs where the Docker network `kind` is routable from the test process, as on GitHub's Linux runners: it dials the tenant's API server at a kind node's address on that network.
Docker Desktop does not route it, so the suite does not run on macOS.
Its files are in `work/e2e/<E2E_CLUSTER>`, one directory for each cluster, so that two runs in one checkout share no kubeconfig: the kubeconfig, the release YAMLs and, after a failure, the artifacts.
The clone of Lodia is `work/lodia`.

## What it installs

In this order:

| component | source | installed by |
|---|---|---|
| cert-manager v1.21.3 | its release YAML | the suite, each Deployment waited on until `Available` |
| Lodia and etcd-druid | the chart of the [Lodia commit](https://github.com/lodia-io/lodia/tree/57375832e7fe8b3a06374613797eb4c544fe7612) that `go.mod` pins, fetched by `make e2e-lodia` into `work/lodia`, with images built by ko into the kind cluster | helm, with `--wait` |
| Cluster API and its kubeadm bootstrap provider v1.15.0-beta.0 | their release YAMLs | clusterctl's `Init` |
| Cluster API provider Docker v1.15.0-beta.0 | the release's `infrastructure-components-development.yaml`, whose image is built for the [staging registry](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/Makefile#L1071-L1074) | clusterctl's `Init` |
| this provider | `make release-components`, the target that renders the release's components YAML, with the image repository `kind.local/cluster-api-provider-lodia` and the host's one platform, so that ko loads the image into the kind cluster | clusterctl's `Init` |

Lodia goes in before the providers because the provider's watches need Lodia's CRDs.
The four providers go in through one `Init` of clusterctl's library, with `WaitProviders`, which waits up to 2 minutes for each of their Deployments, on a local repository that the suite lays out in `work/e2e/<E2E_CLUSTER>/repository` as Cluster API's [`CreateRepository`](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/framework/clusterctl/repository.go#L104-L158) does:
- Cluster API's three releases are there under their own version, each with the `metadata.yaml` of that release;
- the provider's components YAML and the tree's `metadata.yaml` are there under `v<major>.<minor>.99` of the tree's newest series, a version no release has;
- cert-manager is marked as externally provisioned, so that clusterctl waits for the one the suite installed and installs none of its own;
- the `LODIA_KUBEADM_BOOTSTRAP_SA_NAMESPACE` and `LODIA_KUBEADM_BOOTSTRAP_SA_NAME` of the provider's grant are in the configuration file the suite writes, with the namespace and name of the real kubeadm bootstrap provider.

clusterctl reads a variable from the environment before its configuration, for every component alike, so the install fails before it starts when the environment sets a variable that one of the four components' YAMLs references, `EXP_*` and `CAPD_*` ones among them.
It fails the same for `OVERRIDESFOLDER`, which would put another folder of overrides in place of the suite's empty one, whose `components.yaml` and `metadata.yaml` replace the repository's [files](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/repository/overrides.go#L70-L90).
After `Init`, a SubjectAccessReview asks, for the user and the groups of the ServiceAccount of the installed kubeadm bootstrap provider's Deployment, whether they may get and whether they may update `lodiacontrolplanes`: get has to be allowed and update denied.
The rewrite of a ServiceAccount subject into the provider's namespace, which clusterctl does, and a ClusterRole that also grants `update` show there; [`test/components`](../components) holds that the ClusterRole grants `get` alone.

A release YAML is checked against a sha256 kept in [`install_test.go`](install_test.go), and every `image:` in it gets a digest from the same file; an `image:` without one fails the install, and so does any container or init container image of the decoded documents that has none, whatever the shape of its line.
cert-manager's YAML is rendered with Cluster API's `yamlprocessor` at its defaults and applied by the suite; the three Cluster API YAMLs reach clusterctl with their variables, which it processes.
Every create the suite makes itself, cert-manager's and the testdata's, is retried for a minute on a webhook or x509 error, since a webhook can be `Available` before its certificate is in place, which clusterctl [guards](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/cert_manager.go#L565-L571) against with a throwaway Issuer and Certificate; clusterctl retries its own creates.
kind is a `go tool`; ko and kustomize run through `go run` at pinned versions, which keeps them out of `go.mod` (kustomize's is in the `Makefile`, ko's in the `Makefile` and in `tool_test.go`, and `TestTheSuiteAndTheMakefileRunTheSameKo` fails when they differ); helm v4.3.1 comes from the workflow.

To move a pin, change the version, the sum and the digests together, the sum of `metadata.yaml` with them for Cluster API, and the version in the table above.
Read a digest with `go run github.com/google/go-containerregistry/cmd/crane@v0.22.1 digest <image>` and a sum from the release asset.
Lodia's commit is in two places, the pseudo-version of `go.lodia.io/lodia/api` in `go.mod` and `LODIA_COMMIT` in the `Makefile`; `TestLodiaCommitIsThePinnedAPI` fails when they differ.
From Lodia [81ce021](https://github.com/lodia-io/lodia/blob/81ce021f823c6708ba5eacbc5ffe244c80a3ddaf/.ko.yaml) on, its `.ko.yaml` takes the operator's version from `VERSION` in ko's environment, and ko v0.19.1 stops with `map has no entry for key "VERSION"` without it; the suite sets `VERSION` to the first 12 characters of the commit it cloned for the three builds of Lodia.

## The test

`TestAWorkerJoinsAClusterOfLodiasControlPlane` applies the objects of [`testdata`](testdata) in the namespace `capi-join`, and asserts the steps below.
Each waits within a bound of its own, but the third and the seventh, which read at once, the eleventh, whose two waits share one, and the twenty-third, which takes its whole window; the calls between the waits end at their client's request timeout, the kind cluster's or the tenant's, and a `docker` call at a bound of its own, described under "On failure".

1. `Cluster` `ControlPlaneInitialized`.
2. `Cluster.spec.controlPlaneEndpoint` is Lodia's `status.endpoint.apiServer`.
3. `<cluster>-kubeconfig` and `<cluster>-ca` hold the bytes of Lodia's `<cluster>-admin-kubeconfig` and `<cluster>-ca-bundle` under `value` and `tls.crt` and no other key, have the type `cluster.x-k8s.io/secret` and the label `cluster.x-k8s.io/cluster-name`, and the `LodiaControlPlane` controls both.
4. kindnet, from the manifest the node image ships, is applied in the tenant through `<cluster>-kubeconfig`.
5. The `Machine` is `Running` with a `nodeRef`, and `LodiaControlPlane.status.versions` holds the version that the MachineSet's preflight check reads.
6. The tenant's Node has the `DevMachine`'s `providerID`, has lost the `uninitialized` taint and is `Ready`.
7. The worker's container holds the file that its `KubeadmConfigTemplate` renders with `contentFormat: Template` from `{{ .controlPlane.version }}`, and the file holds the `LodiaControlPlane`'s version.
8. The konnectivity agent is ready, and a pod of agnhost, pinned by digest, runs on the Node with its logs readable through the tenant's API server.
9. `Cluster` `Available`.
10. clusterctl's `Move` from the kind cluster to itself fails, and ends within 20 seconds, at its wait for the `block-move` annotation: clusterctl logs that it is blocked on the `LodiaControlPlane`, and the suite ends the move there.
11. Once `Paused` is `True` on the `Cluster` and on the `LodiaControlPlane`, the suite unpauses the `Cluster`, which the move left paused, and `Paused` is `False` on both and the `Cluster`'s `Available` is `True` at an `observedGeneration` of at least the generation that the unpause produced, all within 30 seconds.
    The `Paused` of each controller has then gone `True` and `False`, and the Cluster controller has recomputed `Available` after the unpause.
    The provider's own `Available` carries no generation that the unpause moves, so nothing shows its full pass beyond that.
12. A Deployment of one replica of agnhost, with no placement of its own, runs on the only worker.
13. The MachineDeployment is scaled to 2, and the second `Machine` is `Running` with a `nodeRef`.
14. The second Node has its `DevMachine`'s `providerID`, has lost the `uninitialized` taint and is `Ready`, as step 6 asks of the first.
15. The konnectivity agents are ready on both Nodes, 2 of 2.
16. The tenant is opened again from `<cluster>-kubeconfig` as the provider holds it now, and a list of its Nodes has to be answered.
    The `Machine` whose Node hosts the Deployment's pod gets `cluster.x-k8s.io/delete-machine`, and the MachineDeployment is scaled to 1.
    That `Machine` and its `DevMachine` are gone.
    The other `Machine` is the one it was, by UID, and still `Running` with its `nodeRef`.
    The events of the deleted `Machine` hold `SuccessfulDrainNode` and neither `FailedDrainNode` nor `FailedDeleteNode`.
    Its Node is `NotFound` through the tenant that was opened again.
    The MachineDeployment has 1 replica, ready and available, and the `Cluster` is `Available`.
17. The Deployment's pod runs on the second Node, and its logs are readable through the tenant's API server, opened again at step 16.
18. Every object of the namespace that Cluster API's checks read has the owner references that its kind wants.
    The objects are those of Cluster API, its kubeadm bootstrap provider, CAPD and this provider, Lodia's `ControlPlane` and `Etcd`, and every Secret and ConfigMap.
    A kind without an assertion fails the step, and so does a graph that holds no object of a kind the suite created.
19. With the `Cluster` paused, the owner references of the `LodiaControlPlane` and of Cluster API's, its kubeadm bootstrap provider's and CAPD's objects are removed.
    Once the `Cluster` is unpaused, the check of step 18 holds again within 2 minutes.
20. Every object of the namespace holds exactly the finalizers that its kind wants.
    Those of Lodia and etcd-druid are among them: `lodia.io/datastore` on Lodia's `ControlPlane`, and `druid.gardener.cloud/etcd-druid` on the `Etcd` and on the Secrets that its spec references.
21. With the `Cluster` paused, the finalizers of the `LodiaControlPlane` and of Cluster API's, its kubeadm bootstrap provider's and CAPD's objects are removed.
    Once the `Cluster` is unpaused, the check of step 20 holds again within a minute.
22. The objects of the graph stop changing: four reads of their resourceVersions, 15 seconds apart, each agree with the one before, within 2 minutes.
23. They stay as they are for 2 minutes, read every 5 seconds, but for what Lodia and etcd-druid write.
24. Deleting the `Cluster`, once the etcd claim and the two copied Secrets exist and exactly one container is labelled for the `Cluster`, removes the `LodiaControlPlane`, Lodia's `ControlPlane`, the etcd claim, the two Secrets and the worker's container.

The move is the only way the suite tests that the provider refuses `clusterctl move`.
The provider writes `block-move` on every `LodiaControlPlane`, so clusterctl pauses the `Cluster`, finds the annotation and waits for it to go, which with its [backoff](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/mover.go#L366-L377), 5 seconds growing by 1.5 for ten steps, takes about six minutes before it fails.
The error that ends a move is the context's and names no object, so [`MoveUntilBlocked`](../clusterctlproxy/move.go) reads the message that clusterctl logs when it first sees the annotation, requires it to name the `LodiaControlPlane`, and cancels the move there; the move ends at the wait, after the `Cluster` is paused and before anything is created in the target.
A move whose annotation did not hold would [create](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/mover.go#L1060-L1089) each object in the same cluster, which updates it, and then [delete](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/mover.go#L1260-L1314) the source: the suite fails there, on a `Cluster` that it deletes anyway.
The move leaves the `Cluster` paused, as clusterctl leaves it after any failure once it has made the [pause](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/mover.go#L342-L357), since it [unpauses](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/mover.go#L416-L418) only after it has moved everything.
Step 11 first waits for both controllers to report `Paused` `True`, so that the `False` it waits for later is a write of a controller that has read the `Cluster` unpaused, and not the `False` of before the move: a `LodiaControlPlane` that misses the unpause stays `True`.
It then unpauses the `Cluster` by dropping `spec.paused`, as clusterctl does.
Both controllers stop at `Paused` while it is `True`: Cluster API's Cluster controller [returns](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/cluster/cluster_controller.go#L171-L199) before the deferred update of the status that sets `Available`, so `Available` keeps what it was before the move until the full pass that follows the unpause.
That pass [stamps](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/util/conditions/setter.go#L84) `Available` with the `Cluster`'s generation, so the step requires it `True` at the generation that the unpause produced or a later one; the `Available` of before the move is at an older one.
The `LodiaControlPlane`'s generation does not move with the `Cluster`'s, so its `Paused` going `True` and then `False` is all that shows the provider resumed.
The move's 20 seconds and the 30 of step 11, which its two waits share, are fields of the bounds, which `TestTheBoundsFitUnderTheTimeouts` adds to the others and holds under `-timeout` and the job's `timeout-minutes`.
`TestUnpausingWaitsForBothControllersToReportThePauseBeforeItClearsIt`, `TestUnpausingClearsThePauseOfTheMoveAndWaitsForBothControllersToRunAgain` and `TestUnpausingFailsUnlessBothControllersRanAfterIt` hold step 11's waits and checks on a fake client, which serves what the controllers report and gives the unpause the next generation, and `TestUnpausingTakesOneBoundForBothWaits` that the second wait gets what the first leaves of the bound and not a bound of its own; nothing but a run of the job holds that the step calls them, or step 10.

Steps 12 to 17 hold what the provider owes a MachineDeployment's scale-down.
The Deployment is created while one worker exists, before the scale to 2, so that its pod is on the first Node because that is the only Node there is: a `nodeName` or a `nodeSelector` would keep the replacement `Pending` once that Node is drained.
The `Machine` that hosts the pod is the one marked, since a `Machine` with the annotation [goes first](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_deletion_order.go#L47-L122) in the MachineSet's deletion order, and the pod has the second Node to move to.
The suite patches the annotation and then the replicas, two writes to two kinds, and the MachineSet [lists its Machines](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_controller.go#L707-L714) from the manager's cache, which nothing makes wait for a user's write.
Under the default order `Random` the two `Machine`s then rank alike and the tie [goes by name](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_deletion_order.go#L131-L139), so the other `Machine` could go and the step would fail at its bound on a `Machine` that is "still there".
The MachineDeployment of [`testdata/workers.yaml`](testdata/workers.yaml) therefore has `deletion.order: Oldest`, which the MachineDeployment [copies](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machinedeployment/machinedeployment_rollout_planner.go#L370) to its MachineSet: a `Machine` that is not marked ranks by its [age](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_deletion_order.go#L47-L76), and the marked `Machine` is the first worker, since the pod was placed while it was the only Node, so the annotation and the order pick the same one.
Cluster API's own scale spec [counts](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/framework/machinedeployment_helpers.go#L551-L560) the `Machine`s that have a `nodeRef` and nothing else, in a [scale](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/e2e/md_scale.go#L111-L126) that never looks at the Nodes, so it passes a provider whose Node deletion fails; step 16 reads the events and the Node, and step 17 the pod.
The drain and the deletion of the Node go through `<cluster>-kubeconfig`, the Secret that the provider copies: the Machine controller's client for the workload cluster is [built from it](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/controllers/clustercache/cluster_accessor_client.go#L125-L131), the [drain](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L888-L891) and the [deletion of the Node](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L1054-L1070) use it, and so does the [`nodeRef` of the second `Machine`](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller_noderef.go#L79-L83).
The ClusterCache reads the Secret only [when it is not connected](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/controllers/clustercache/cluster_cache.go#L496-L507), and its [health probe](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/controllers/clustercache/cluster_accessor.go#L327-L375) runs on the connection it holds, which it [drops](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/controllers/clustercache/cluster_cache.go#L531-L534) only when the server refuses that connection's own credential or five probes in a row fail.
A copy that the provider rewrites after the first join with a credential that does not authenticate therefore goes unseen by the drain, the deletion of the Node and the second `nodeRef`, which go on through the connection they have, so every check that reads Cluster API's objects passes.
Step 16 opens the tenant again from the Secret as it is then and requires a list of the Nodes to be answered, before it reads anything else: a copy that does not authenticate fails there, with the Secret's name.
Every read through the tenant that the steps make from then on, the Node of the deleted `Machine` and step 17's pod and logs among them, goes through that client.
`TestTheTenantIsOpenedAgainFromTheSecretAsTheProviderHoldsItNow` holds the re-opening against a tenant that refuses a credential, one that a client opened before the rewrite still holds; nothing but a run of the job holds that step 16 calls it.
A credential revoked at the tenant's API server, which the provider cannot do, takes the ClusterCache's own path: the health probe is refused, the connection is dropped, and the next one [fails](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/controllers/clustercache/cluster_accessor_client.go#L216-L219) on the credential that the Secret holds.
That keeps the second `Machine` from its `nodeRef` at step 13, or, if it has one already, fails the drain of step 16 with the event `FailedDrainNode`, which Cluster API [records and retries](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L561-L568) until the bound ends.
A control plane whose `status.externalManagedControlPlane` is not `true` makes Cluster API [answer](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L855-L874) `errNoControlPlaneNodes` for the deletion of a worker, which it [accepts without a word](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L493-L503): it skips the [drain](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L505-L576) and the [deletion of the Node](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L667-L686) and still [removes the `Machine`'s finalizer](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L699) once the infrastructure is gone.
The `Machine` goes all the same, so a check that ends on the `Machine` being gone passes: step 16 fails on the missing `SuccessfulDrainNode`, the first of its checks that the skipped drain fails, and the check of the Node would fail it on the Node that is left behind if the event check did not.
The bounds of steps 13, 14 and 15 are those of the waits of steps 5, 6 and 8, which they repeat for the second worker.
Step 12 has a minute, since agnhost is on the Node already; step 16 has three, for a drain that waits for the pods' termination and for one of Cluster API's [20-second retries](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L75), the removal of the container and the deletion of the Node; step 17 has two, for agnhost's pull onto the second Node.
All six are fields of the bounds, `Deployed`, `ScaleUp`, `ScaleReady`, `ScaleAgents`, `ScaleDown` and `Rescheduled`.
`TestEveryWaitOfTheJoinTestIsBoundedByAFieldOfTheBoundsThatNoOtherWaitTakes` holds that every wait of `join_test.go` takes a field of the bounds and that no field bounds two of them, since `TestTheBoundsFitUnderTheTimeouts` counts each field once.
The waits it knows are `until`, `requireUnpaused`, `whilePaused`, `settle`, `hold` and `context.WithTimeout`, each with the argument that bounds it; it refuses a `time.Sleep`, a call of `wait` and the other waits of `time` and `context` in the test, a `bounds.<field>` that is not the bound of one of the known waits, a field that bounds no wait, and `Install` and `Dump`, which bound the install and the dump, anywhere in the test.
`TestTheCheckOfTheWaitsRefusesWhatBreaksTheSumOfTheBounds` holds the check itself on snippets of each of these.
`TestAScaleDownIsDoneWhenTheMachineAndEverythingItOwnedAreGoneAndTheOtherStays`, `TestTheDrainOfAMachineIsHeldByTheEventsOfThatMachineAlone`, `TestANodeHasJoinedWhenItsProviderIDIsTheDevMachinesAndItIsUntaintedAndReady` and the tests beside them hold the checks of steps 13 to 17 on fake clients, the management cluster's and the tenant's apart; nothing but a run of the job holds that the steps call them.

Steps 18 to 23 are Cluster API's [quick start checks](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/e2e/quick_start_test.go#L40-L81), written as plain functions on the suite's client.
Cluster API's helpers read the objects through `GetOwnerGraph`, which [builds](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/ownergraph.go#L71-L72) a clusterctl proxy of its own from a kubeconfig path, so the suite lists the graph itself, as `GetOwnerGraph` [does](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/ownergraph.go#L93-L149): the namespaced kinds of the CRDs that carry the label `clusterctl.cluster.x-k8s.io`, at their [storage version](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/objectgraph.go#L346-L412), and the Secrets and ConfigMaps, in the `Cluster`'s namespace.
Only an install through clusterctl labels the CRDs of Cluster API, its kubeadm bootstrap provider, CAPD and this provider.
Lodia's CRDs and etcd-druid's carry no such label, so the suite adds Lodia's `ControlPlane` and the `Etcd` by hand.
A graph that holds no object of a kind the suite created fails every check, since a CRD that lost its label would otherwise hide its objects from them.
The cluster-scoped kinds are left out: Cluster API's check keeps them only when their names contain the `Cluster`'s, and the suite creates none.
The steps run after the scale-down and before the deletion, so that they read the shape of objects that the deletion starts from.
The stability check is the last, as in Cluster API's spec, since the pauses of steps 19 and 21 write to every object.

The owners are [Cluster API's assertions](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/framework/ownerreference_helpers.go#L164-L357) for its own kinds and the suite's for the others.
The `LodiaControlPlane` is owned, not controlled, by the `Cluster`.
Lodia's `ControlPlane` is controlled by the `LodiaControlPlane`, the `Etcd` by the `ControlPlane`, and a Secret or ConfigMap by the `ControlPlane`, the `Etcd` or, for the bootstrap data, a `KubeadmConfig`, except that `<cluster>-kubeconfig` and `<cluster>-ca` are controlled by the `LodiaControlPlane` alone.
Every owner reference has to name an object of the namespace, by its UID, which the `KubeadmConfig` that the deleted `Machine` leaves for the garbage collector does not until it is gone, and step 19 would otherwise leave it with no owner for good.
A provider whose apply of the `ControlPlane` drops its owner reference leaves it with none, which step 18 names.
Step 19 removes the owner references of the kinds that Cluster API and the provider put back once the `Cluster` is unpaused, as [Cluster API's check](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/framework/ownerreference_helpers.go#L459-L475) does for every object of its graph.
It leaves Lodia's `ControlPlane` and `Etcd` and every Secret and ConfigMap alone.
The provider refuses to adopt a `ControlPlane` or a Secret that it does not control, so as never to take a predecessor's ([`docs/design.md`](../../docs/design.md), held by [`foreign_test.go`](../../internal/controller/foreign_test.go) and [`races_test.go`](../../internal/controller/races_test.go)): an owner reference removed from them would stay removed, and the garbage collector would then leave them behind at step 24.
Lodia and etcd-druid do not follow the `Cluster`'s pause, and the bootstrap data's owner is the kubeadm bootstrap provider's to put back.
Both removals wait for `Paused` `True` on the `Cluster` and on the `LodiaControlPlane` first, which only a controller that has seen the pause writes, and lift the pause afterwards, also when the removal failed.

The finalizers are compared as a whole set, as [Cluster API's check](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/framework/finalizers_helpers.go#L123-L153) does, an empty set for a kind without an assertion, so that a finalizer nobody expects fails the step.
Cluster API's own assertion for the `DevCluster` fails here, since CAPD gives an externally managed one [no finalizer](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/infrastructure/docker/reconcilers/devcluster_reconciler.go#L103-L107), which the suite's `DevCluster` is.
etcd-druid holds every Secret that an `Etcd` [references](https://github.com/gardener/etcd-druid/blob/v0.39.0/internal/controller/secret/reconciler.go#L71-L100) with its finalizer, so the step reads the names from the `Etcd`'s spec; the Secrets of Lodia's that it does not reference hold none.
Step 21 removes only what Cluster API's controllers and the provider hold.
The provider and Cluster API's controllers add their finalizers before they read the pause ([the Cluster's](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/cluster/cluster_controller.go#L161-L171), for one), so step 21 shows that the finalizers are back, and not that a full reconcile has resumed since the unpause.
A provider that never adds its finalizer fails step 20, and one that adds it once and never puts it back fails step 21.

Step 22 and step 23 follow [Cluster API's spec](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/framework/resourceversion_helpers.go#L44-L76): four reads that agree with the one before, the first read having none to agree with, and then a window over which nothing changes, with [intervals](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/e2e/config/docker.yaml#L272-L273) of 2 minutes at 15 seconds and 2 minutes at 5 seconds.
The objects are stamped by their resourceVersion but for two.
The `Etcd` is left out: etcd-druid [rewrites](https://github.com/gardener/etcd-druid/blob/v0.39.0/internal/controller/etcd/reconciler.go#L147) its status every 15 seconds with a new `lastUpdateTime`, which Lodia's own [watch](https://github.com/lodia-io/lodia/blob/57375832e7fe8b3a06374613797eb4c544fe7612/internal/controller/datastore/etcd.go#L397-L407) filters out.
Lodia's `ControlPlane` is stamped by the provider's own entry of `managedFields`, `cluster-api-provider-lodia`, since Lodia writes its status: an apply that changes nothing leaves the entry's time and the resourceVersion as they were, and one that changes something moves the time, which kube-apiserver 1.35.0 under envtest showed for a ConfigMap applied twice and then changed.
A `ControlPlane` without that entry fails the step, since nothing would show a loop of the provider's.
A provider that changes the `ControlPlane` on every pass is such a loop, since each write comes back through its watch of the `ControlPlane`: step 22 never reads four that agree.
One that changes it from time to time fails step 23.
The window takes its whole 2 minutes whenever it passes, and its length is Cluster API's, not measured on CI yet.

The eight new bounds are the fields `Owners`, `OwnersPaused`, `OwnersRestored`, `Finalizers`, `FinalizersPaused`, `FinalizersRestored`, `Settled` and `Stable`:
- 30 seconds for steps 18 and 20, which read at once but for what the scale-down leaves to be deleted, and for each pause to be seen by the two controllers;
- 2 minutes and 1 minute for the owner references and the finalizers to come back, Cluster API's [5 minutes](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/framework/ownerreference_helpers.go#L109-L138) and [1 minute](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/framework/finalizers_helpers.go#L98-L101) cut to what a reconcile after an unpause needs;
- 2 minutes each for steps 22 and 23, Cluster API's.
They add 9 minutes to the others, which raised `-timeout` from 55 to 64 minutes and the job's `timeout-minutes` from 65 to 74.
The steps take about 4 minutes when nothing is slow: a read of the graph is a list of every kind, a few seconds, each pause and its restore some 10 to 20 seconds, step 22 at least 60 seconds, four intervals of 15, and step 23 exactly 120.
That is an estimate, not a measurement.
`TestEveryWaitOfTheJoinTestIsBoundedByAFieldOfTheBoundsThatNoOtherWaitTakes` holds their waits as it holds those of steps 12 to 17.
`TestTheGraphHoldsTheLabelledKindsOfTheNamespaceAndTheSecretsAndConfigMapsAndLodiasTwo`, `TestEveryObjectOfTheGraphHasTheOwnersItsKindWants`, `TestEveryObjectOfTheGraphHoldsExactlyTheFinalizersItsKindWants`, `TestAnActionRunsOnlyOnceBothControllersReportPausedAndTheClusterIsUnpausedAfterIt`, `TestTheStampsHoldWhatTheProviderWritesAndNotWhatLodiaAndEtcdDruidDo`, `TestSettleReturnsAfterFourReadsInARowThatAgree`, `TestHoldFailsAtTheFirstChangeAndOtherwiseTakesTheWholeWindow` and the tests beside them hold the checks of steps 18 to 23 on fake clients; nothing but a run of the job holds that the steps call them.

The `DevCluster` carries the annotation `cluster.x-k8s.io/managed-by`, which Cluster API [reads as an annotation](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/util/annotations/helpers.go#L38-L41), so that CAPD [leaves it alone](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/infrastructure/docker/reconcilers/devcluster_reconciler.go#L103-L107): otherwise CAPD starts a load balancer, writes its address into the `DevCluster`'s endpoint ([CAPD](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/infrastructure/docker/reconcilers/backends/docker/dockercluster_backend.go#L102-L106)), and the Cluster takes it before the control plane's ([Cluster](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/cluster/cluster_controller_phases.go#L217-L228)).
The infrastructure contract [gives](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/docs/book/src/developer/providers/contracts/infra-cluster.md?plain=1#L475-L490) the rest to whoever manages such an infrastructure, so the suite patches the one field `DevCluster.status.initialization.provisioned` once.
No assertion reads it.

## On failure

The suite writes to `work/e2e/<E2E_CLUSTER>/artifacts`, and CI uploads it: the objects above with their conditions and Lodia's `Etcd`, the metadata of the Secrets and ConfigMaps of `capi-join`, without data or annotations, and of the CRDs, the pods, logs and events of cert-manager, of the managers of Cluster API, CAPD, Lodia and the provider, and of the control plane in `capi-join`, through `<cluster>-kubeconfig` once it exists the tenant's Nodes, DaemonSets, Deployments and ReplicaSets, and the pods and events of `kube-system` and `default`, and from the worker container `journalctl -u kubelet -u containerd` and `crictl ps -a`.
`make e2e` empties the directory before it starts.
A cancelled job and a `go test` timeout leave no artifacts, since the test binary writes them and neither lets it finish.
The bounds in [`bounds_test.go`](bounds_test.go), the install's and the dump's among them, add up to less than `-timeout`, and `-timeout` to less than the job's `timeout-minutes`, so that a step's own bound fails first; `TestTheBoundsFitUnderTheTimeouts` fails when they do not.
A request to the tenant has a timeout of its own, 30 seconds in the steps and an eighth of the dump's 30 seconds for the tenant in the dump, since controller-runtime's REST mapper [discovers](https://github.com/kubernetes-sigs/controller-runtime/blob/v0.25.2/pkg/client/apiutil/restmapper.go#L285) without the request's context, and a tenant that does not answer would hold a step or the dump past its bound.
A discovery asks `/api`, `/apis` and the version of a group, so a step against such a tenant fails at most three requests after its bound, and the dump stops listing the tenant once its bound has passed, which ends it at most one discovery, three eighths of the bound, after it.
The dump's requests to the kind cluster, the pods' logs among them, have a timeout of 10 seconds for the same reason, and the dump stops listing once its own bound has passed, so a kind cluster that does not answer ends it at most one discovery after its bound.
The pods' logs go last, after the tenant: a kubelet that does not answer holds every log request to that timeout, in each container, and would leave the tenant nothing.
The dump reads the worker containers first, within 30 seconds of their own, since `docker` does not depend on the API server: a kind cluster that does not answer uses what remains of the dump's 2 minutes and would leave them nothing, and a `docker` that hangs ends at the 30 seconds and leaves the kind cluster and the tenant the rest.
The install's and the steps' client for the kind cluster has a timeout of 75 seconds on every request, creates included.
That is above the 60 seconds after which kube-apiserver [answers](https://github.com/kubernetes/kubernetes/blob/v1.37.2/staging/src/k8s.io/apiserver/pkg/server/config.go#L453) a request that is not long-running, and it [ignores](https://github.com/kubernetes/kubernetes/blob/v1.37.2/staging/src/k8s.io/apiserver/pkg/endpoints/filters/request_deadline.go#L81-L89) a longer `timeout` query, so the client never cuts a call that the server would answer: a create waits for the webhooks of its object, 30 seconds for cert-manager's, inside those 60.
Its discovery has a timeout of 10 seconds, through a REST mapper of its own, since the mapper discovers without the request's context.
clusterctl's own proxy gives requests and discovery one timeout of 30 seconds, and loads `KUBECONFIG` and `~/.kube/config` with their current context where a call names no kubeconfig, as an empty `FromKubeconfig` of a move does.
The suite gives clusterctl a [Proxy of its own](../clusterctlproxy/proxy.go) instead, over the rest config of the guarded kubeconfig and with the client's two timeouts, for both ends of every call; the factory refuses a kubeconfig that the Proxy would ignore.
`TestInitAndMoveAgainstAClusterThatDoesNotAnswerEndWithinTheirBoundAndOneDiscoveryTimeout` in that package fails a Proxy without the discovery mapper, which overshoots by the request timeout in a `Move` and in an `Init` against a cluster that answers its version and never its discovery, and `TestNoCallReadsAKubeconfigOrTheCurrentContext` a call that falls back to `KUBECONFIG`.
`TestEveryClusterClientTheFactoryMakesReachesTheClusterOfTheRestConfig` holds that the client the factory makes for either end of a move, the one that names no kubeconfig and the one that names the Proxy's, reaches the rest config's cluster with its request timeout, under a `KUBECONFIG` that names another.
`TestEveryClusterctlClientIsBuiltThroughTheFactory` fails, outside the Proxy's [`proxy.go`](../clusterctlproxy/proxy.go), every call into clusterctl's `client` and `client/cluster` packages but for `cluster.InjectProxy` and `cluster.InjectYamlProcessor`, `cluster.GetOwnerGraph`, which makes clusterctl's own proxy from a kubeconfig path, among them, and every import of Cluster API's `test/framework`, whose clients take a kubeconfig path too.
`TestTheClusterctlClientEndsItsCallsAtTheSuitesTimeouts` holds the same for the suite's own wiring of the two timeouts, and `TestTheClusterctlClientsRequestsAskForTheirOwnTimeouts` that the version check and the discovery of an `Init` ask for the discovery timeout and the inventory's request for the client's.
A kind cluster that does not answer ends a wait of a step at most one discovery after its bound, and a call between the waits within a discovery, three requests of 10 seconds, and then the 75 seconds.
A step's context has no deadline, so `docker` ends every call it makes at a bound of its own, 30 seconds, whoever calls it: a `docker` that hangs fails steps 4, 7 and 24 there, and inside the wait of step 24 fails the call, which the next poll repeats.
The dump's workers have a bound over all their calls besides, which ends the call that is running at its end.
`TestADockerCallThatHangsEndsAtItsBound` holds the call's bound for a caller without a deadline and for one with a later deadline, and `TestADockerCallThatHangsEndsWithItsCallersContext` an earlier deadline of its caller.
`TestTheBoundsFitUnderTheTimeouts` holds that three requests, with the tenant's or the dump's timeout, fit in the time left for the calls without a bound, that the client's timeout is above the API server's and fits there after a discovery of three requests, that the three discovery requests of a client's first call, which clusterctl asks without a context, fit there as well, counted as four with the version check for margin, that a `docker` call's bound fits there too, and that the workers' bound and twice the tenant's are together less than the dump's, so that a `docker` that hangs leaves the kind cluster and the tenant more than twice the tenant's bound.
Go kills a test binary one minute after its `-timeout`, counted from its start, while its own alarm counts from the end of the install.
CAPD does not retry a failed bootstrap; the output of `kubeadm join` is in the `BootstrapCompleted` condition of the `DevMachine`.
