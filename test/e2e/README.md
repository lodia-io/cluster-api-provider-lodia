# End-to-end test

The suite runs only against a kind cluster whose kubeconfig is named on the command line, in `E2E_KUBECONFIG`, and refuses any other: [`guard.go`](guard.go) wants a single context whose name starts with `kind-capl-e2e` and whose server is a loopback address, as kind writes it, so it never reaches a cluster through the current kube context or one that only carries the name.
The prefix is not Lodia's `lodia-e2e`: this guard refuses Lodia's own e2e cluster, `kind-lodia-e2e-local`, in which the suite would upgrade Lodia, and Lodia's guard refuses this one.
It also refuses to start while a `HELM_KUBE*` variable is set, since helm [lays them over](https://github.com/helm/helm/blob/v4.3.1/pkg/cli/environment.go#L97-L130) `--kubeconfig`.

`make e2e` creates the kind cluster `capl-e2e`, runs the suite and deletes the cluster.
`make e2e-upgrade` runs [the upgrade test](#the-upgrade-test) the same way on the kind cluster `capl-e2e-upgrade`, in `work/e2e/capl-e2e-upgrade`, so that the two targets share neither a cluster nor a directory; `E2E_UPGRADE_CLUSTER` changes its name, and `E2E_CLUSTER` on the command line overrides it.
`make e2e-minor` runs [the minor step test](#the-minor-step-test) the same way on the kind cluster `capl-e2e-minor`, in `work/e2e/capl-e2e-minor`, so that no two targets share a cluster or a directory; `E2E_MINOR_CLUSTER` changes its name, and `E2E_CLUSTER` on the command line overrides it.
`E2E_CLUSTER` changes the name.
`make e2e` refuses, before it creates anything, a name that does not start with `capl-e2e`, that has a character outside `a-z`, `0-9` and `-`, that ends in `-w` or that is longer than 30 characters.
The prefix is the one the guard wants, and a name ending in `-w` is refused because a run named `x` removes the containers labelled `x-w`, which are also the nodes of a kind cluster named `x-w`.
The Cluster is named `<E2E_CLUSTER>-w`: CAPD [labels](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/infrastructure/docker/internal/docker/util.go#L31) its containers with the Cluster's name in kind's own [label](https://github.com/kubernetes-sigs/kind/blob/v0.33.0/pkg/cluster/internal/providers/docker/constants.go#L21) for the nodes of a cluster, so that name must not be the kind cluster's, and Lodia [requires](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/api/v1alpha1/controlplane_types.go#L18) the name of the `ControlPlane`, the Cluster's, to be a DNS-1035 label of at most 32 characters.
The cluster has one node of kind's default image, with the Docker socket that CAPD needs and the admission plugin `OwnerReferencesPermissionEnforcement`, which [refuses](https://github.com/kubernetes/kubernetes/blob/v1.37.0/plugin/pkg/admission/gc/gc_admission.go#L149) an owner reference with `blockOwnerDeletion` to an object whose finalizers the writer cannot set.
After it creates the cluster and again at the end, `make e2e` removes the containers labelled for the Cluster, with their volumes; on a Linux host, delete the cluster of a killed run first: `go tool kind delete cluster --name capl-e2e --kubeconfig work/e2e/capl-e2e/kubeconfig`.

The suite needs Docker and helm on the `PATH`, and runs where the Docker network `kind` is routable from the test process, as on GitHub's Linux runners: it dials the tenant's API server at a kind node's address on that network.
Docker Desktop does not route it, so the suite does not run on macOS.
Its files are in `work/e2e/<E2E_CLUSTER>`, one directory for each cluster, so that two runs in one checkout share no kubeconfig: the kubeconfig, the release YAMLs and, after a failure, the artifacts.
The clone of Lodia is `work/lodia`.

## What it installs

In this order:

| component | source | installed by |
|---|---|---|
| cert-manager v1.21.3 | its release YAML | the suite, each Deployment waited on until `Available` |
| Lodia and etcd-druid | the chart of the [Lodia commit](https://github.com/lodia-io/lodia/tree/f91168b1248dc18151a0c2d442fe2050593a0866) that `go.mod` pins, fetched by `make e2e-lodia` into `work/lodia`, with images built by ko into the kind cluster | helm, with `--wait` |
| Cluster API and its kubeadm bootstrap provider v1.15.0-beta.0 | their release YAMLs | clusterctl's `Init` |
| Cluster API provider Docker v1.15.0-beta.0 | the release's `infrastructure-components-development.yaml`, whose image is built for the [staging registry](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/Makefile#L1071-L1074) | clusterctl's `Init` |
| this provider | `make release-components`, the target that renders the release's components YAML, with the image repository `kind.local/cluster-api-provider-lodia` and the host's one platform, so that ko loads the image into the kind cluster | clusterctl's `Init` |

`make e2e-upgrade` installs the previous release of the provider in place of the last row, and the tree's build beside it in the repository, as [the upgrade test](#the-upgrade-test) says.
`make e2e-minor` installs what `make e2e` does.
Lodia goes in before the providers because the provider's watches need Lodia's CRDs.
The four providers go in through one `Init` of clusterctl's library, with `WaitProviders`, which waits up to 2 minutes for each of their Deployments, on a local repository that the suite lays out in `work/e2e/<E2E_CLUSTER>/repository` as Cluster API's [`CreateRepository`](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/framework/clusterctl/repository.go#L104-L158) does:
- Cluster API's three releases are there under their own version, each with the `metadata.yaml` of that release;
- the provider's components YAML and the tree's `metadata.yaml` are there under `v<major>.<minor>.99` of the tree's newest series, a version no release has;
- cert-manager is marked as externally provisioned, so that clusterctl waits for the one the suite installed and installs none of its own;
- the `LODIA_KUBEADM_BOOTSTRAP_SA_NAMESPACE` and `LODIA_KUBEADM_BOOTSTRAP_SA_NAME` of the provider's grant are in the configuration file the suite writes, with the namespace and name of the real kubeadm bootstrap provider.

clusterctl reads a variable from the environment before its configuration, for every component alike, so the install fails before it starts when the environment sets a variable that one of the four components' YAMLs references, `EXP_*` and `CAPD_*` ones among them.
It fails the same for `OVERRIDESFOLDER`, which would put another folder of overrides in place of the suite's empty one, whose `components.yaml` and `metadata.yaml` replace the repository's [files](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/repository/overrides.go#L70-L90).
After `Init`, a SubjectAccessReview asks, for the user and the groups of the ServiceAccount of the installed kubeadm bootstrap provider's Deployment, whether they may get and whether they may update `lodiacontrolplanes`: get has to be allowed and update denied.
The rewrite of a ServiceAccount subject into the provider's namespace, which clusterctl does, and a ClusterRole that also grants `update` show there; [`test/components`](../components) holds that the ClusterRole grants `get` alone.

A release YAML is checked against a sha256 kept in [`install_test.go`](install_test.go), and every `image:` in it gets a digest from the same file; an `image:` without one fails the install, and so does any container or init container image of the decoded documents that has none, whatever the shape of its line.
cert-manager's YAML is rendered with Cluster API's `yamlprocessor` at its defaults and applied by the suite; the three Cluster API YAMLs reach clusterctl with their variables, which it processes.
Every create that the install and the first step of each test make themselves, cert-manager's and the testdata's, is retried for a minute on a webhook or x509 error, since a webhook can be `Available` before its certificate is in place, which clusterctl [guards](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/cert_manager.go#L565-L571) against with a throwaway Issuer and Certificate; clusterctl retries its own creates.
The creates of `md-1`'s objects at step 7 of the minor step test are made once and not retried, since the webhooks of the same kinds have answered at its first step.
kind is a `go tool`; ko and kustomize run through `go run` at pinned versions, which keeps them out of `go.mod` (kustomize's is in the `Makefile`, ko's in the `Makefile` and in `tool_test.go`, and `TestTheSuiteAndTheMakefileRunTheSameKo` fails when they differ); helm v4.3.1 comes from the workflow.

To move a pin, change the version, the sum and the digests together, the sum of `metadata.yaml` with them for Cluster API, and the version in the table above.
Read a digest with `go run github.com/google/go-containerregistry/cmd/crane@v0.22.1 digest <image>` and a sum from the release asset.
Lodia's commit is in three places, the pseudo-version of `go.lodia.io/lodia/api` in `go.mod` and in `api/go.mod`, and `LODIA_COMMIT` in the `Makefile`; `TestLodiaCommitIsThePinnedAPI` fails when `go.mod` and the `Makefile` differ, and `TestTheAPIModulePinsWhatTheMainModuleDoes` when the two `go.mod` files differ on that module or on `sigs.k8s.io/cluster-api/api`.
Lodia's [`.ko.yaml`](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/.ko.yaml#L3-L7) takes the operator's version from `VERSION` in ko's environment, and ko v0.19.1 stops with `map has no entry for key "VERSION"` without it; the suite sets `VERSION` to the first 12 characters of the commit it cloned for the three builds of Lodia.

## The test

`TestAWorkerJoinsAClusterOfLodiasControlPlane` applies the objects of [`testdata`](testdata) in the namespace `capi-join`, and asserts the steps below.
Each waits within a bound of its own, but the third and the seventh, which read at once, the eleventh, whose two waits share one, the nineteenth and the twenty-first, whose pause and removal share the first of their two with the waits around them, and the twenty-third, which takes its whole window; the unpause of the eleventh, the nineteenth and the twenty-first has a bound of its own; the calls between the waits end at their client's request timeout, the kind cluster's or the tenant's, and a `docker` call at a bound of its own, described under "On failure".

1. `Cluster` `ControlPlaneInitialized`.
2. `Cluster.spec.controlPlaneEndpoint` is Lodia's `status.endpoint.apiServer`.
3. `<cluster>-kubeconfig` and `<cluster>-ca` hold the bytes of Lodia's `<cluster>-admin-kubeconfig` and `<cluster>-ca-bundle` under `value` and `tls.crt` and no other key, have the type `cluster.x-k8s.io/secret` and the label `cluster.x-k8s.io/cluster-name`, and the `LodiaControlPlane` controls both.
4. kindnet, from the manifest the node image ships, is applied in the tenant through `<cluster>-kubeconfig`.
5. The `Machine` is `Running` with a `nodeRef`, and `LodiaControlPlane.status.versions` holds the version that the MachineSet's preflight check reads.
6. The tenant's Node has the `DevMachine`'s `providerID`, has lost the `uninitialized` taint and is `Ready`.
7. The worker's container holds the file that its `KubeadmConfigTemplate` renders with `contentFormat: Template` from `{{ .controlPlane.version }}`, and the file holds the `LodiaControlPlane`'s version.
8. The konnectivity agent is ready, and a pod of agnhost, pinned by digest, runs on the Node with its logs readable through the tenant's API server.
9. `Cluster` `Available`.
10. clusterctl's `Move` from the kind cluster to itself fails, and ends within 20 seconds, at its wait for the `block-move` annotation: clusterctl logs that it is blocked on the `LodiaControlPlane`, and the suite ends the move there.
11. Once `Paused` is `True` on the `Cluster` and on the `LodiaControlPlane`, the suite unpauses the `Cluster`, which the move left paused, and `Paused` is `False` on both and the `Cluster`'s `Available` is `True` at an `observedGeneration` of at least the generation that the unpause produced, all within 30 seconds.
    The `Paused` of each controller has then gone `True` and `False`, and the Cluster controller has recomputed `Available` after the unpause.
    The provider's own `Available` carries no generation that the unpause moves, so nothing shows its full pass beyond that.
12. A Deployment of one replica of agnhost, with no placement of its own, runs on the only worker.
13. The MachineDeployment is scaled to 2, and the second `Machine` is `Running` with a `nodeRef`.
14. The second Node has its `DevMachine`'s `providerID`, has lost the `uninitialized` taint and is `Ready`, as step 6 asks of the first.
15. The konnectivity agents are ready on both Nodes, 2 of 2.
16. The tenant is opened again from `<cluster>-kubeconfig` as the provider holds it now, and a list of its Nodes has to be answered.
    The `Machine` whose Node hosts the Deployment's pod gets `cluster.x-k8s.io/delete-machine`, and the MachineDeployment is scaled to 1.
    That `Machine` and its `DevMachine` are gone.
    The other `Machine` is the one it was, by UID, and still `Running` with its `nodeRef`.
    The events of the deleted `Machine` hold `SuccessfulDrainNode` and neither `FailedDrainNode` nor `FailedDeleteNode`.
    Its Node is `NotFound` through the tenant that was opened again.
    The MachineDeployment has 1 replica, ready and available, and the `Cluster` is `Available`.
17. The Deployment's pod runs on the second Node, and its logs are readable through the tenant's API server, opened again at step 16.
18. Every object of the namespace that Cluster API's checks read has the owner references that its kind wants.
    The objects are those of Cluster API, its kubeadm bootstrap provider, CAPD and this provider, Lodia's `ControlPlane` and `Etcd`, and every Secret and ConfigMap.
    A kind without an assertion fails the step, and so does a graph that holds no object of a kind the suite created.
19. With the `Cluster` paused, the owner references of the `LodiaControlPlane`, of Cluster API's, its kubeadm bootstrap provider's and CAPD's objects, and of the bootstrap data's Secret are removed.
    Once the `Cluster` is unpaused, `Paused` is `False` on the `Cluster` and the `LodiaControlPlane` and the `Cluster`'s `Available` is `True` at the unpause's generation or later, as at step 11, all within 30 seconds of the pause.
    The check of step 18 then holds again within 2 minutes.
20. Every object of the namespace holds exactly the finalizers that its kind wants.
    Those of Lodia and etcd-druid are among them: `lodia.io/datastore` on Lodia's `ControlPlane`, and `druid.gardener.cloud/etcd-druid` on the `Etcd` and on the Secrets that its spec references.
21. With the `Cluster` paused, the finalizers of the `LodiaControlPlane` and of Cluster API's, its kubeadm bootstrap provider's and CAPD's objects are removed.
    Once the `Cluster` is unpaused, `Paused` is `False` on both and the `Cluster`'s `Available` is `True` at the unpause's generation or later, all within 30 seconds of the pause.
    The check of step 20 then holds again within a minute.
22. The objects of the graph stop changing: four reads of their resourceVersions, 15 seconds apart, each agree with the one before, within 2 minutes.
23. They stay as they are for 2 minutes, read every 5 seconds, but for what Lodia and etcd-druid write.
24. Deleting the `Cluster`, once the etcd claim and the two copied Secrets exist and exactly one container is labelled for the `Cluster`, removes the `LodiaControlPlane`, Lodia's `ControlPlane`, the etcd claim, the two Secrets and the worker's container.

The move is the only way the suite tests that the provider refuses `clusterctl move`.
The provider writes `block-move` on every `LodiaControlPlane`, so clusterctl pauses the `Cluster`, finds the annotation and waits for it to go, which with its [backoff](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/mover.go#L366-L377), 5 seconds growing by 1.5 for ten steps, takes about six minutes before it fails.
The error that ends a move is the context's and names no object, so [`MoveUntilBlocked`](../clusterctlproxy/move.go) reads the message that clusterctl logs when it first sees the annotation, requires it to name the `LodiaControlPlane`, and cancels the move there; the move ends at the wait, after the `Cluster` is paused and before anything is created in the target.
A move whose annotation did not hold would [create](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/mover.go#L1060-L1089) each object in the same cluster, which updates it, and then [delete](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/mover.go#L1260-L1314) the source: the suite fails there, on a `Cluster` that it deletes anyway.
The move leaves the `Cluster` paused, as clusterctl leaves it after any failure once it has made the [pause](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/mover.go#L342-L357), since it [unpauses](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/mover.go#L416-L418) only after it has moved everything.
Step 11 first waits for both controllers to report `Paused` `True`, so that the `False` it waits for later is a write of a controller that has read the `Cluster` unpaused, and not the `False` of before the move: a `LodiaControlPlane` that misses the unpause stays `True`.
It then unpauses the `Cluster` by dropping `spec.paused`, as clusterctl does.
Both controllers stop at `Paused` while it is `True`: Cluster API's Cluster controller [returns](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/cluster/cluster_controller.go#L171-L199) before the deferred update of the status that sets `Available`, so `Available` keeps what it was before the move until the full pass that follows the unpause.
That pass [stamps](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/util/conditions/setter.go#L84) `Available` with the `Cluster`'s generation, so the step requires it `True` at the generation that the unpause produced or a later one; the `Available` of before the move is at an older one.
The `LodiaControlPlane`'s generation does not move with the `Cluster`'s, so its `Paused` going `True` and then `False` is all that shows the provider resumed.
The move's 20 seconds and the 30 of step 11, which its two waits share, are fields of the bounds, which `TestTheBoundsFitUnderTheTimeouts` adds to the others and holds under `-timeout` and the job's `timeout-minutes`.
`TestUnpausingWaitsForBothControllersToReportThePauseBeforeItClearsIt`, `TestUnpausingClearsThePauseOfTheMoveAndWaitsForBothControllersToRunAgain` and `TestUnpausingFailsUnlessBothControllersRanAfterIt` hold step 11's waits and checks on a fake client, which serves what the controllers report and gives the unpause the next generation, and `TestUnpausingTakesOneBoundForBothWaits` that the second wait gets what the first leaves of the bound and not a bound of its own; nothing but a run of the job holds that the step calls them, or step 10.

Steps 12 to 17 hold what the provider owes a MachineDeployment's scale-down.
The Deployment is created while one worker exists, before the scale to 2, so that its pod is on the first Node because that is the only Node there is: a `nodeName` or a `nodeSelector` would keep the replacement `Pending` once that Node is drained.
The `Machine` that hosts the pod is the one marked, since a `Machine` with the annotation [goes first](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_deletion_order.go#L47-L122) in the MachineSet's deletion order, and the pod has the second Node to move to.
The suite patches the annotation and then the replicas, two writes to two kinds, and the MachineSet [lists its Machines](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_controller.go#L707-L714) from the manager's cache, which nothing makes wait for a user's write.
Under the default order `Random` the two `Machine`s then rank alike and the tie [goes by name](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_deletion_order.go#L131-L139), so the other `Machine` could go and the step would fail at its bound on a `Machine` that is "still there".
The MachineDeployment of [`testdata/workers.yaml`](testdata/workers.yaml) therefore has `deletion.order: Oldest`, which the MachineDeployment [copies](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machinedeployment/machinedeployment_rollout_planner.go#L370) to its MachineSet: a `Machine` that is not marked ranks by its [age](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_deletion_order.go#L47-L76), and the marked `Machine` is the first worker, since the pod was placed while it was the only Node, so the annotation and the order pick the same one.
Cluster API's own scale spec [counts](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/framework/machinedeployment_helpers.go#L551-L560) the `Machine`s that have a `nodeRef` and nothing else, in a [scale](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/e2e/md_scale.go#L111-L126) that never looks at the Nodes, so it passes a provider whose Node deletion fails; step 16 reads the events and the Node, and step 17 the pod.
The drain and the deletion of the Node go through `<cluster>-kubeconfig`, the Secret that the provider copies: the Machine controller's client for the workload cluster is [built from it](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/controllers/clustercache/cluster_accessor_client.go#L125-L131), the [drain](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L888-L891) and the [deletion of the Node](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L1054-L1070) use it, and so does the [`nodeRef` of the second `Machine`](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller_noderef.go#L79-L83).
The ClusterCache reads the Secret only [when it is not connected](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/controllers/clustercache/cluster_cache.go#L496-L507), and its [health probe](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/controllers/clustercache/cluster_accessor.go#L327-L375) runs on the connection it holds, which it [drops](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/controllers/clustercache/cluster_cache.go#L531-L534) only when the server refuses that connection's own credential or five probes in a row fail.
A copy that the provider rewrites after the first join with a credential that does not authenticate therefore goes unseen by the drain, the deletion of the Node and the second `nodeRef`, which go on through the connection they have, so every check that reads Cluster API's objects passes.
Step 16 opens the tenant again from the Secret as it is then and requires a list of the Nodes to be answered, before it reads anything else: a copy that does not authenticate fails there, with the Secret's name.
Every read through the tenant that the steps make from then on, the Node of the deleted `Machine` and step 17's pod and logs among them, goes through that client.
`TestTheTenantIsOpenedAgainFromTheSecretAsTheProviderHoldsItNow` holds the re-opening against a tenant that refuses a credential, one that a client opened before the rewrite still holds; nothing but a run of the job holds that step 16 calls it.
A credential revoked at the tenant's API server, which the provider cannot do, takes the ClusterCache's own path: the health probe is refused, the connection is dropped, and the next one [fails](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/controllers/clustercache/cluster_accessor_client.go#L216-L219) on the credential that the Secret holds.
That keeps the second `Machine` from its `nodeRef` at step 13, or, if it has one already, fails the drain of step 16 with the event `FailedDrainNode`, which Cluster API [records and retries](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L561-L568) until the bound ends.
A control plane whose `status.externalManagedControlPlane` is not `true` makes Cluster API [answer](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L855-L874) `errNoControlPlaneNodes` for the deletion of a worker, which it [accepts without a word](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L493-L503): it skips the [drain](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L505-L576) and the [deletion of the Node](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L667-L686) and still [removes the `Machine`'s finalizer](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L699) once the infrastructure is gone.
The `Machine` goes all the same, so a check that ends on the `Machine` being gone passes: step 16 fails on the missing `SuccessfulDrainNode`, the first of its checks that the skipped drain fails, and the check of the Node would fail it on the Node that is left behind if the event check did not.
The bounds of steps 13, 14 and 15 are those of the waits of steps 5, 6 and 8, which they repeat for the second worker.
Step 12 has a minute, since agnhost is on the Node already; step 16 has three, for a drain that waits for the pods' termination and for one of Cluster API's [20-second retries](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machine/machine_controller.go#L75), the removal of the container and the deletion of the Node; step 17 has two, for agnhost's pull onto the second Node.
All six are fields of the bounds, `Deployed`, `ScaleUp`, `ScaleReady`, `ScaleAgents`, `ScaleDown` and `Rescheduled`.
`TestEveryWaitOfTheJoinTestIsBoundedByAFieldOfTheBoundsThatNoOtherWaitTakes` holds that every wait of `join_test.go` is bounded by a field of the bounds and that no field bounds two of them, since `TestTheBoundsFitUnderTheTimeouts` counts each field once.
The waits that take their bound as an argument are `until`, `requireUnpaused`, `whilePaused`, `pauseCycle`, `settle`, `hold`, `endAfter` and `context.WithTimeout`, and the argument has to be a field of the bounds.
The waits that take it from the context they run on are `pollUntil`, `apply`, `applyRelease`, `available`, `installCertManager`, `deploymentsAvailable`, `deploymentAvailableWithin` and `clusterctlproxy.MoveUntilBlocked`, and their context has to be a variable that the same step made with `endAfter` from a field of the bounds: a call on the step's own context, which has no deadline, on one that `context.WithTimeout` made, which ends by a deadline, on one that another step made, or on a variable that the step has assigned since it made the context, is refused.

## The upgrade test

`make e2e-upgrade` runs `TestTheProviderUpgradesFromThePreviousRelease` alone, with `-run` and the build tags `e2e` and `upgrade`, on the kind cluster `capl-e2e-upgrade` that it creates and deletes as `make e2e` does its own; CI runs it as the job `e2e-upgrade`, on every pull request and every push to `main`, beside the job `e2e`.
The tags split the tests: `join_test.go` is behind `e2e` and neither `upgrade` nor `minor`, `upgrade_test.go` and `lodia_upgrade_test.go` behind both `e2e` and `upgrade`, `minor_test.go` behind `e2e` and `minor`, and `suite_test.go`, `install_test.go` and `steps_test.go`, which hold the install and the steps that the three tests share, behind `e2e`.
`lodia_join_test.go`, behind `e2e` and not `upgrade`, gives the install the tree's build for the join test and for the minor step test, and `lodia_upgrade_test.go` the release and the tree's build.
It is a job of its own, and not a step of the join test or a test on its cluster:
- the join test's Cluster is made by the tree's build that `Init` installs, and an upgrade from a release needs the release running when the Cluster is made, so installing the release there would leave the tree's `Init` and its creation of the `ControlPlane` and the Secrets untested ([the decision](../../docs/decisions/e2e-on-a-named-cluster.md));
- a management cluster holds one instance of the provider, which clusterctl's upgrade [checks](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/upgrader.go#L375-L379), so the release could follow the join test on its cluster only after a `clusterctl delete` and an `Init` of the release, a downgrade that no user runs, and the two tests would depend on their order;
- Cluster API runs each of its upgrade specs on a management cluster of its own, a [kind cluster](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/e2e/clusterctl_upgrade.go#L283-L296) or a workload cluster made into one.

The unit tests of the package, about a minute of them on CI, run in `make verify` and in the join job, so the upgrade job leaves them out and its bounds need no time for them.
`TestTheBoundsFitUnderTheTimeouts` holds the `-run` of the target, and that the job's build tags compile a file that declares that test, since `go test` with a pattern that matches nothing passes.
It holds also that every test of a file with a build tag is compiled by one job and no other, since a job that compiles another job's test runs it on its own cluster beside its own, outside its bounds, and a test that no job compiles runs nowhere.
It holds that the one job that compiles such a file runs each of its tests, since a job with a `-run` runs its own test alone and passes without the others: [`TestEachJobIsHeldToTheTestsOfTheFilesItsBuildTagsCompile`](bounds_test.go) holds those two checks on files of its own.
It holds also that a job adds up the set of bounds that `waitedFiles` names for the file whose tests the job compiles, the set that the check of the waits holds for that file, so that the model counts the waits the job runs: [`TestEachJobIsHeldToTheBoundsOfTheWaitsOfItsTests`](bounds_test.go) holds that check on files of its own.
The three jobs run on three runners in parallel, so the join job keeps its 64 and 74 minutes.

The reasons for the checks:
- clusterctl deletes the namespaced objects of the provider and the ServiceAccount among them, and keeps the CRDs, the Namespace, the inventory and every cluster-scoped object whose name does not start with the provider's namespace and a dash ([delete](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/components.go#L153-L199)), which are all five ClusterRoles and ClusterRoleBindings of the render, the grant's among them, and the custom resources of CRDs that carry the provider label, which it does not [list](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/proxy.go#L245-L263); it installs into the namespace of the inventory, so a Namespace that the tree renames leaves nothing behind ([the target namespace](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/upgrader.go#L364-L367));
- it creates each object or merge-patches it over what is there ([create](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/components.go#L95-L131)), so the CRDs and the five keep their UIDs and take every field that the tree sets, while a label, an annotation or a field that a release drops stays, since a [JSON merge patch](https://www.rfc-editor.org/rfc/rfc7386#section-2) leaves what it does not name ([`client.Merge`](https://github.com/kubernetes-sigs/controller-runtime/blob/v0.25.2/pkg/client/patch.go#L34-L36)), and a binding whose `roleRef` changes fails the upgrade;
- no storage migration runs for a provider's CRDs, since clusterctl's migrator [serves](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/cert_manager.go#L298-L305) cert-manager alone, so the storage version of the release has to stay listed, served or not, since the API server converts through every version of `spec.versions` ([converter](https://github.com/kubernetes/kubernetes/blob/v1.37.2/staging/src/k8s.io/apiextensions-apiserver/pkg/apiserver/conversion/converter.go#L58-L62)) and refuses a CRD whose `status.storedVersions` names a version that is not listed ([validation](https://github.com/kubernetes/kubernetes/blob/v1.37.2/staging/src/k8s.io/apiextensions-apiserver/pkg/apis/apiextensions/validation/validation.go#L263-L287)); a version that was served has to stay served for another reason, that clusterctl [counts](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/upgrader.go#L660-L676) a version that stops being served, `served: false` included, and [refuses](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/client/cluster/upgrader.go#L641-L656) the upgrade where a ClusterClass names it;
- the `readyz` of the manager is a ping, so clusterctl, which waits for the Deployment to be `Available` when the call sets `WaitProviders` and otherwise does not ([the flag](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/cmd/clusterctl/cmd/upgrade_apply.go#L92-L93)), returns before the new manager leads: the old manager keeps its Lease, since the manager sets no `LeaderElectionReleaseOnCancel`, and the new one waits out the lease that the old manager's record names, 1 minute from the duration in [`main.go`](../../cmd/cluster-api-provider-lodia/main.go), counted from its first read of the record and not from its own duration ([the check](https://github.com/kubernetes/client-go/blob/v0.37.2/tools/leaderelection/leaderelection.go#L485-L494), [the lease](https://github.com/kubernetes/client-go/blob/v0.37.2/tools/leaderelection/leaderelection.go#L548-L554)), and then up to 11 seconds more, a retry period of 5 jittered by a factor of 1.2 ([the loop](https://github.com/kubernetes/client-go/blob/v0.37.2/tools/leaderelection/leaderelection.go#L259-L274), [the factor](https://github.com/kubernetes/client-go/blob/v0.37.2/tools/leaderelection/leaderelection.go#L72), [`Jitter`](https://github.com/kubernetes/apimachinery/blob/v0.37.2/pkg/util/wait/wait.go#L92-L98));
- the holder of the Lease is the pod's host name, which is its name, and a UUID ([source](https://github.com/kubernetes-sigs/controller-runtime/blob/v0.25.2/pkg/leaderelection/leader_election.go#L93-L97)), and the old pod can still be terminating, for its 10 seconds of grace ([`manager.yaml`](../../config/manager/manager.yaml)), when the old Deployment reports no replica, so this test's step 11 orders the pause after the new manager;
- the pause cycle shows the new manager reconciling the same `LodiaControlPlane`: its writes are where the tree's schema first meets an object that the release wrote;
- the times of last transition of `Available` are kept by anything that does not flap: a poll could miss a flap, the time cannot;
- Cluster API checks the same of its own upgrade, [no unexpected rollouts](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/e2e/clusterctl_upgrade.go#L677-L679) and [the resourceVersions stable](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/e2e/clusterctl_upgrade.go#L746-L753) after the last upgrade, so a new manager that rewrites what the old one wrote fails steps 15 and 16 when what it writes brings its own pass back, Lodia's `ControlPlane` or the `LodiaControlPlane`: a copied Secret is not watched, the sync period of 10 minutes ([`main.go`](../../cmd/cluster-api-provider-lodia/main.go)) does not come round in the hold, and the passes stop;

What the test holds today is clusterctl's mechanics and the adoption of the release's objects by a new pod; its reach grows with every change of the manifests, the CRDs and the controller on `main`.

### The reads of step 7

The `LodiaControlPlane` copies Lodia's `status.kubernetes.version`, the oldest version of the API server, the controller manager, the scheduler and the addons, which moves once the last of them is done and in the same write that removes `status.kubernetes.upgrade` ([the version](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/docs/decisions/upgrades-and-maintenance-windows.md?plain=1#L16-L17), [the status](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/internal/controller/lifecycle/decide.go#L121-L123), [the fields](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/api/v1alpha1/controlplane_types.go#L809-L822)).
Each poll of the wait reads in this order: it lists the `Machine`s of `md-1`, then reads the `LodiaControlPlane`, then Lodia's `ControlPlane`.
- A `Machine` of `md-1` while the `LodiaControlPlane` read after it says v1.36.4 fails the step.
  The MachineSet creates a `Machine` only while no entry of `status.versions` is below `spec.version` ([the check](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_preflight.go#L186-L197), [upgrading](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/internal/contract/controlplane.go#L295-L353)), and the copy only moves forward, so a `Machine` that exists before the copy read after it says v1.37.0 was created under an upgrade.
- A `LodiaControlPlane` of v1.37.0 while Lodia's `ControlPlane` read after it still has `status.kubernetes.upgrade` or a part that does not run v1.37.0, among `status.components.apiServer`, `controllerManager`, `scheduler` and `status.addons`, fails the step.
  Lodia's report only moves forward as well, so a read made after the copy shows at least what the copy was made from.
  A provider that copies a version that runs ahead of Lodia's report by more than a poll fails here: `spec.version`, `status.target.version` and `status.components.apiServer.version` do ([the steps](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/docs/decisions/upgrades-and-maintenance-windows.md?plain=1#L19-L31)).
  A copy of the controller manager's or the scheduler's version may pass, since Workloads renders both at `status.components.apiServer.version` and Tenant renders the addons at the oldest of the three components ([the renderers](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/docs/decisions/upgrades-and-maintenance-windows.md?plain=1#L12-L14)), so it runs ahead of `status.kubernetes.version` only from the later of the two reports to the apply of the addons, and the step sees it only when a poll falls in that window.
- The MachineSet of `md-1` has to say once that the control plane is upgrading: its `ScalingUp` names `ControlPlaneIsStable` and "is upgrading" ([the message](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_controller_status.go#L111-L175), [the check](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_preflight.go#L196)).
  The absence of a `Machine` alone would also be that of a MachineSet that scales up nothing, so this is the positive proof of the hold.
  The message is Cluster API's text, so a bump that changes it fails every run.
- A failure of the wait carries what the last poll read: the version the `LodiaControlPlane` reports, the parts of Lodia's `ControlPlane` that are behind, and its `Progressing`, which says why a step waits ([Progressing](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/docs/decisions/upgrades-and-maintenance-windows.md?plain=1#L117)).

A read that breaks a rule ends the wait from inside its check, with the violation kept, and the step fails after the wait, so the waits stay plain `until`s on fields of `minorBounds`, which the check of the waits holds.
No sleep and no window of its own is needed: the hold lasts as long as the roll, and a poll comes every 2 seconds.
The MachineSet comes back to the hold every 15 seconds ([the requeue](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_controller.go#L1045-L1057), [the period](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_preflight.go#L45-L47)) and watches no control plane ([the watches](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_controller.go#L156-L178)), so `md-1`'s `Machine` comes up to 15 seconds after the version is reported.
The `Ready` of the `LodiaControlPlane` may read `Unknown` with `LatestGenerationNotObserved` between the edit and Lodia's next report ([`report`](../../internal/controller/lodiacontrolplane.go)): the step logs each change of it and asserts nothing of it.

### Why `md-1`, and why these versions

- A scale-up of `md-0` would prove nothing: from the edit on, the kubeadm check holds new `Machine`s of v1.36.4 for good, during the roll and after it, since it wants the control plane's minor ([the check](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_preflight.go#L218-L236)).
  `md-1` at v1.37.0 is held by the Kubernetes check before the edit ([the check](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_preflight.go#L202-L216)), by `ControlPlaneIsStable` alone during the roll, and by nothing after it.
- The running worker is left alone: `md-0`'s template does not change, so nothing rolls it out, and Lodia moves kube-proxy, CoreDNS and konnectivity-agent onto its Node without waiting for them and counts its kubelet as outdated ([the steps](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/docs/decisions/upgrades-and-maintenance-windows.md?plain=1#L27-L30), [`status.nodes`](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/docs/api/controlplane.md?plain=1#L102)).
- v1.36.4 to v1.37.0 are two minors of Lodia's table ([the table](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/internal/versions/versions.go#L36-L40)), and a v1.36 kubelet under a v1.37 API server is inside the skew that Lodia's preflight and Cluster API's Kubernetes check apply ([Lodia](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/internal/controller/lifecycle/decide.go#L401-L407), [Cluster API](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/core/reconcilers/machineset/machineset_preflight.go#L202-L216)).
  A pin of Lodia whose table lacks v1.36 leaves the Cluster at step 2 with `Unsupported` in `Progressing` ([the condition](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/docs/api/controlplane.md?plain=1#L129)), and the pair then moves to the two newest minors.
- CAPD takes a worker's image from the `Machine`'s version ([the create](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/infrastructure/docker/internal/docker/machine.go#L224-L250)), from the digests that its mapper holds for both versions ([the mapper](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/infrastructure/kind/mapper.go#L84-L94)); a patch it has no digest for gets a bare tag ([`GetMapping`](https://github.com/kubernetes-sigs/cluster-api/blob/v1.15.0-beta.0/test/infrastructure/kind/mapper.go#L643-L690)), so the pair stays on mapped patches and needs no `customImage`.
  The mapper is in CAPD's release, whose manager the suite pins by digest.
- A class without a backup store holds nothing: the `Backup` reports `NoBackupStore` on its first pass, before any credential is read, and Lifecycle moves the target on it ([the report](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/internal/controller/datastore/backup.go#L196-L198), [the target](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/internal/controller/lifecycle/decide.go#L457-L462)).
  The suite sets no `maintenance`: patch updates are off by default ([the field](https://github.com/lodia-io/lodia/blob/f91168b1248dc18151a0c2d442fe2050593a0866/docs/api/controlplane.md?plain=1#L55)), and on they would start the tenant above `spec.version` ([a version in status](../../docs/README.md#a-version-in-status)).

### The bounds

`minorBounds` in [`bounds_test.go`](bounds_test.go), with `Install` and `Dump` of the join test's set, fit the job's `-timeout` and `timeout-minutes`:

| `Apply`, `Initialized`, `Kindnet`, `Running`, `Ready`, `Available` | 1, 4, 1, 3, 3 and 1 minutes | steps 1 to 6, the join test's waits at v1.36.4; the image of v1.36.4, which the mapper names without a registry, so that docker pulls it from Docker Hub, is pulled inside `Running`, which no run has measured |

They add up to 28 minutes, and with `Install` and `Dump` to 45, which `TestTheBoundsFitUnderTheTimeouts` fits under `-timeout 47m` of `make e2e-minor` and `timeout-minutes: 57` of the job, as it fits the other two.
`TestAJobAddsTheInstallAndTheDumpToTheBoundsOfAnySetButTheJoinTests` holds that `Install` and `Dump` of the join test's set are in the sum of each of the other two jobs.
Both fit with no spare minute: the 45 and the 2 minutes of calls without a bound are the 47, and the 47 and the 10 minutes outside the binary are the 57.
`TestEveryWaitOfTheMinorTestIsBoundedByAFieldOfItsOwnBoundsThatNoOtherWaitTakes` holds every wait of `minor_test.go` to a field of `minorBounds` that no other wait takes, and `TestEachTargetThatRunsTheSuiteCreatesAClusterOfItsOwnThatTheGuardAccepts` that the three targets share no cluster and no directory.
About 6 minutes of test after the install is an estimate, not a measurement.

The checks of steps 5 to 10 are plain functions that `stepped_test.go` holds on fake clients: `TestAMinorStepIsHeldOrBrokenAsTheOrderedReadsOfEachPollSayAndTheHoldIsSeenOnce` holds the rules of step 7 on a script of what each read finds, with the order of the reads, `TestAPollListsTheMachinesThenReadsTheCopyThenLodiasReport` and the tests beside it.

## On failure

The suite writes to `work/e2e/<E2E_CLUSTER>/artifacts`, and CI uploads it: the objects above with their conditions and Lodia's `Etcd`, the metadata of the Secrets and ConfigMaps of `capi-join`, without data or annotations, and of the CRDs, the pods, logs and events of cert-manager, of the managers of Cluster API, CAPD, Lodia and the provider, and of the control plane in `capi-join`, through `<cluster>-kubeconfig` once it exists the tenant's Nodes, DaemonSets, Deployments and ReplicaSets, and the pods and events of `kube-system` and `default`, and from the worker container `journalctl -u kubelet -u containerd` and `crictl ps -a`.
`make e2e` empties the directory before it starts.
A cancelled job and a `go test` timeout leave no artifacts, since the test binary writes them and neither lets it finish.
The bounds in [`bounds_test.go`](bounds_test.go), the install's and the dump's among them, add up to less than `-timeout`, and `-timeout` to less than the job's `timeout-minutes`, so that a step's own bound fails first; `TestTheBoundsFitUnderTheTimeouts` fails when they do not, and reads `-timeout` from the one line of the target's recipe in the `Makefile` that runs `go test`, with the tags of the job's test.
A request to the tenant has a timeout of its own, 30 seconds in the steps and an eighth of the dump's 30 seconds for the tenant in the dump, since controller-runtime's REST mapper [discovers](https://github.com/kubernetes-sigs/controller-runtime/blob/v0.25.2/pkg/client/apiutil/restmapper.go#L285) without the request's context, and a tenant that does not answer would hold a step or the dump past its bound.
A discovery asks `/api`, `/apis` and the version of a group, so a step against such a tenant fails at most three requests after its bound, and the first call of a client that a step opens between its waits, step 16's list of Nodes, takes its own request besides, four, and the dump stops listing the tenant once its bound has passed, which ends it at most one discovery, three eighths of the bound, after it.
The dump's requests to the kind cluster, the pods' logs among them, have a timeout of 10 seconds for the same reason, and the dump stops listing once its own bound has passed, so a kind cluster that does not answer ends it at most one discovery after its bound.
The pods' logs go last, after the tenant: a kubelet that does not answer holds every log request to that timeout, in each container, and would leave the tenant nothing.
The dump reads the worker containers first, within 30 seconds of their own, since `docker` does not depend on the API server: a kind cluster that does not answer uses what remains of the dump's 2 minutes and would leave them nothing, and a `docker` that hangs ends at the 30 seconds and leaves the kind cluster and the tenant the rest.
The install's and the steps' client for the kind cluster has a timeout of 75 seconds on every request, creates included.
That is above the 60 seconds after which kube-apiserver [answers](https://github.com/kubernetes/kubernetes/blob/v1.37.2/staging/src/k8s.io/apiserver/pkg/server/config.go#L453) a request that is not long-running, and it [ignores](https://github.com/kubernetes/kubernetes/blob/v1.37.2/staging/src/k8s.io/apiserver/pkg/endpoints/filters/request_deadline.go#L81-L89) a longer `timeout` query, so the client never cuts a call that the server would answer: a create waits for the webhooks of its object, 30 seconds for cert-manager's, inside those 60.
Its discovery has a timeout of 10 seconds, through a REST mapper of its own, since the mapper discovers without the request's context.
clusterctl's own proxy gives requests and discovery one timeout of 30 seconds, and loads `KUBECONFIG` and `~/.kube/config` with their current context where a call names no kubeconfig, as an empty `FromKubeconfig` of a move does.
The suite gives clusterctl a [Proxy of its own](../clusterctlproxy/proxy.go) instead, over the rest config of the guarded kubeconfig and with the client's two timeouts, for both ends of every call; the factory refuses a kubeconfig that the Proxy would ignore.
`TestEveryCallAgainstAClusterThatDoesNotAnswerEndsWithinItsBoundAndOneDiscoveryTimeout` in that package fails a Proxy without the discovery mapper, which overshoots by the request timeout in a `Move`, an `Init` and an `ApplyUpgrade` against a cluster that answers its version and never its discovery, and `TestNoCallReadsAKubeconfigOrTheCurrentContext` a call that falls back to `KUBECONFIG`.
`TestEveryClusterClientTheFactoryMakesReachesTheClusterOfTheRestConfig` holds that the client the factory makes for either end of a move, the one that names no kubeconfig and the one that names the Proxy's, reaches the rest config's cluster with its request timeout, under a `KUBECONFIG` that names another.
`TestEveryClusterctlClientIsBuiltThroughTheFactory` fails, outside the Proxy's [`proxy.go`](../clusterctlproxy/proxy.go) and the trap's [`trap_test.go`](../clusterctlproxy/trap_test.go), which builds clusterctl's own proxy to see that the trap holds it, every call into clusterctl's `client` and `client/cluster` packages but for `cluster.InjectProxy` and `cluster.InjectYamlProcessor`, `cluster.GetOwnerGraph`, which makes clusterctl's own proxy from a kubeconfig path, among them, and a walk that reads no Go file in a directory that holds a package of the module.
`TestNoPackageOfTheDependencyGraphBuildsClusterctlClientsFromAPath` fails, with and without the `e2e` tag, a package of Cluster API's `test/e2e` or `test/framework` in the dependency graph under any import name, since their clients take a kubeconfig path too, and any other package outside the module and clusterctl's own that imports clusterctl's `client` or `client/cluster`.
Every test outside the suite's tagged files that builds a clusterctl client through the factory, the envtest `Move` among them, first calls [`TrapTheDefaultKubeconfig`](../clusterctlproxy/trap.go), which points `KUBECONFIG` at a kubeconfig of a cluster that never answers and fails the test if that cluster is asked anything, so that a factory that falls back to clusterctl's own proxy fails the tests and does not reach the developer's current context.
The suite's tagged files, those with the build tag `e2e`, build theirs on the rest config of the cluster that the guard accepted and call no trap.
`TestTheTrapIsWhatClientGoAndClusterctlsOwnProxyLoadWhereNoKubeconfigIsNamed` holds that client-go's default loading rules and clusterctl's own proxy, with no context and with `Kubeconfig`'s, load the trap's cluster, and `TestTheTrapFailsTheTestOnlyWhenItsClusterIsAsked` that a test that reaches it fails.
`TestTheClusterctlClientEndsItsCallsAtTheSuitesTimeouts` holds that `Init`, `Move` and `ApplyUpgrade` through the suite's own wiring of the two timeouts end within their bound and one discovery timeout, and `TestTheClusterctlClientsRequestsAskForTheirOwnTimeouts` that the version check and the discovery of an `Init`, and the discovery of an `ApplyUpgrade`, ask for the discovery timeout, and the inventory's request of the one and the Cluster CRD's of the other for the client's.
A kind cluster that does not answer ends a wait of a step at most one discovery after its bound, and a call between the waits within a discovery, three requests of 10 seconds, and then the 75 seconds.
A step's context has no deadline, so `docker` ends every call it makes at a bound of its own, 30 seconds, whoever calls it: a `docker` that hangs fails steps 4, 7 and 24 there, and inside the wait of step 24 fails the call, which the next poll repeats.
The dump's workers have a bound over all their calls besides, which ends the call that is running at its end.
`TestADockerCallThatHangsEndsAtItsBound` holds the call's bound for a caller without a deadline and for one with a later deadline, and `TestADockerCallThatHangsEndsWithItsCallersContext` an earlier deadline of its caller.
`TestTheBoundsFitUnderTheTimeouts` holds that four requests with the tenant's timeout, a new client's three of discovery and its own, and three with the dump's, fit in the time left for the calls without a bound, that the client's timeout is above the API server's and fits there after a discovery of three requests, that the three discovery requests of a client's first call, which clusterctl asks without a context, fit there as well, counted as four with the version check for margin, that a `docker` call's bound fits there too, that the unpause's own bound and two discoveries, the one that cuts a failed step short and the unpause's, fit there as well, and that the workers' bound and twice the tenant's are together less than the dump's, so that a `docker` that hangs leaves the kind cluster and the tenant more than twice the tenant's bound.
Go kills a test binary one minute after its `-timeout`, counted from its start, while its own alarm counts from the end of the install.
